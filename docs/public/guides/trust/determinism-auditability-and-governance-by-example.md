# Guide: Determinism, Auditability, and Governance

This guide is for operators, workflow authors, and technical evaluators who need to inspect the evidence Transist preserves for a run.

> **Prerequisites:** You should be familiar with the concepts in the guides for [Inspecting Runs](../inspection/inspecting-runs-artifacts-evidence-and-events.md) and [Managing Secrets](secrets-and-runtime-policy-in-practice.md).
>
> **Conceptual Background:** For a deeper dive, see the handbook page on [Determinism and Auditability](../../handbook/04-trust-and-runtime-behavior/01-determinism-and-auditability.md).

## The Goal

To give you a concrete understanding of where to find the evidence that proves what a workflow did, how it did it, and when. You will learn to identify:

- The complete event history of a run.
- The final persisted state.
- The artifacts and evidence produced.
- The clear boundaries where your workflow interacts with the outside world.

## The Trust Checklist: What Makes a Run Auditable?

For any completed workflow run, you can answer the following questions from persisted Transist records, subject to the limits of external tools and systems. All the evidence locations below are relative to the effective Transist home directory — resolve it with `transist home get` (by default `${XDG_STATE_HOME:-$HOME/.local/state}/transist`).

1. **What was the exact workflow definition?**
    The compiled "recipe" for your workflow is saved, capturing the exact version that was executed.
    *Evidence Location:* `<home>/registry/recipes/<workflow-id>-<version>.yaml`

2. **What was the final state of every step?**
    The `state.json` file records the final inputs, outputs, and status for every step that was attempted. It is the current-state projection; the append-only history is carried by `events.jsonl`, `failures.jsonl`, execution records, and execution-scoped artifacts/evidence.
    *Evidence Location:* `<home>/runs/run_<run-ref>/state.json`

3. **What is the complete timeline of events?**
    The `events.jsonl` file is an immutable, append-only log of everything that happened during the run, from the moment it started to the moment it finished.
    *Evidence Location:* `<home>/runs/run_<run-ref>/events.jsonl`

4. **What files did the workflow produce?**
    Any artifacts generated by the workflow (e.g., reports, logs, binaries) are stored in a dedicated directory, linked directly to the step that created them.
    *Evidence Location:* `<home>/runs/run_<run-ref>/artifacts/<step-id>/`

5. **Were any secrets exposed?**
    As covered in the [secrets guide](secrets-and-runtime-policy-in-practice.md), raw secret values resolved by Transist are redacted from Transist-managed persisted data. Plugins and tools must still avoid emitting derived secrets.

## Where Determinism Begins and Ends

It's crucial to understand what Transist does and does not control.

**Transist provides deterministic runtime semantics.**
This means the workflow's shape, the order of steps, the identity of the plugins, and the way state is recorded are all predictable and auditable.

**Transist does *not* make external systems deterministic.**
If your workflow calls an external tool, that tool is still subject to the real world.

- A shell command that checks the time will return a different value every second.
- An HTTP request to a flaky API might fail one time and succeed the next.

Transist's job is not to change reality. Its job is to record the **boundary** between your workflow and the outside world where the adapter and plugin expose that information. You can inspect persisted requests, responses, artifacts, evidence, and events that Transist receives or records.

## What "Governance" Means in Practice

Governance is about having the visibility and control to enforce your rules. For any given workflow run, you can prove:

- **What boundary was crossed?** (e.g., a local `process`, a networked `http` call).
- **Which tool was used?** (e.g., the `shell` plugin, action `exec`).
- **What policy was enforced?** (e.g., was secret delivery allowed for this adapter?).
- **What was the exact result?** (e.g., the exit code, the HTTP response, the files produced).

This level of detail helps teams build workflows that are reviewable, governable, and suitable for controlled rollout.
