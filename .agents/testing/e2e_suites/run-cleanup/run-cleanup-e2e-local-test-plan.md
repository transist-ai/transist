# Run Cleanup E2E Local Test Plan

## Goal

Verify that every explicit `success`, `canceled`, or `failed` cleanup branch runs
automatically on its matching root outcome, preserving that primary outcome.
Keep explicit cleanup as a separate recovery scenario.

## Execution

After building `target/debug/transist`, run:

```bash
bash .agents/testing/e2e_suites/run-cleanup/run.sh
```

Or use the harness:

```bash
python3 .agents/testing/run_e2e.py --suite run-cleanup
```

`run.sh` is the executable source of truth. It needs Python 3, `jq`, and the
bundled shell plugin. It creates a fresh standalone home and a separate temporary
workspace root; neither contains the other. Catalog references and the synthetic
recovery fixture use `0.1.0`. Run creation uses the positional workflow reference
and `--run-ref`; recovery commands take the positional run reference.

## Scenarios and Acceptance Criteria

### 1. Boot and install

- Initialize a standalone home, install the bundled shell plugin and cleanup demo.
- Check `demo_09_cleanup_branches@0.1.0` and assert its compiled recipe exists.

### 2. Automatic success cleanup

- Start the demo with `fail=false slow=false` in a fresh workspace.
- Await persisted `status: success`, cleanup trigger `success`, cleanup state
  `succeeded`, and exactly one successful `on_success` execution.
- Verify `cleanup-success.txt` content and absence of the other branch markers.

### 3. Automatic failed cleanup and resume rejection

- Start the demo with `fail=true` in another workspace.
- Await persisted `status: failed` and successful automatic failed cleanup,
  including exactly one `on_failed` execution and the matching marker.
- Do not invoke `runs cleanup` for this normal failure.
- After runner finalization, attempt `runs resume`; require a nonzero result with
  a cleanup-related diagnostic, `recovery_state: cleanup_completed`, unchanged
  failed status, and the same successful single cleanup execution and marker.

### 4. Automatic canceled cleanup

- Start the slow demo and wait for the main step's persisted active process
  invocation before canceling it.
- Require the cancel report to identify the root, acknowledge cancellation, report
  `settled: true`, final status `canceled`, and `cleanup_state: succeeded`, with no
  cancellation error. Settlement includes teardown and root lease release.
- Await cleanup trigger `canceled`, cleanup state `succeeded`, and one successful
  `on_canceled` execution. Verify only the canceled marker exists.
- Do not invoke `runs cleanup` for this normal cancellation.

### 5. Inactive cancellation rejection

- Complete another successful run and its automatic cleanup.
- Require `runs cancel` to reject it with the inactive-run diagnostic.

### 6. Explicit recovery after deliberately failed cleanup

- Install a synthetic `e2e_cleanup_recovery@0.1.0` fixture generated by `run.sh`.
  Primary work fails; teardown fails until a workspace readiness marker exists.
- Await automatic cleanup failure, `recovery_state: cleanup_required`, and one
  teardown execution. Confirm no recovered marker exists.
- After the first runner finishes, create the readiness marker and invoke
  `runs cleanup` once.
- Require successful cleanup, `recovery_state: cleanup_completed`, preserved
  primary failure, two teardown attempts, and only one primary execution.
- Verify the recovered marker and exact teardown-attempt count.

## Synchronization and Teardown

All waits poll bounded persisted state, active invocation records, or trusted
runner lifecycle events. Terminal primary status alone does not prove cleanup or
lease finalization. Each successful scenario awaits the latest runner `finished`
event before another mutation or removal of its home.

Readiness checks inspect both the logical run directory and the isolated home's
private `.transist-staging/invoke-*/active_invocations/` records: staging rewrites
the adapter-visible `run_root`. Require exact run ID, step ID, adapter kind, and
the invocation ID from the persisted step request. Log the matched record path;
on timeout, dump persisted state and observed invocation records instead of
silently treating an unmatched logical-root glob as readiness evidence.

The companion [run-cancellation suite](../run-cancellation/run-cancellation-e2e-local-test-plan.md)
holds direct and nested canceled cleanup open while repeatedly canceling root and
contained identities. It verifies the same live cleanup invocation survives and
only root cleanup runs.

The exit trap removes the ephemeral home and workspaces. These fixtures use no
network services, real secrets, manual gates, or remote inspector.
